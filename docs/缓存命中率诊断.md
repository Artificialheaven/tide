# 缓存命中率诊断报告

> 数据源：`deepseek.db` 的 `usage_log` 表（本群 187593231），统计到 2026-10-27 15:20。
> 口径：命中率 = cache_hit / tokens_in；未命中 = tokens_in - cache_hit。

## 一、一句话结论

盘子没崩：chat 的整体命中率 **92.80%**，一半轮次的未命中只有 450 token 左右（≈1.5%，属于正常波动）。
真正拉低观感的是**少数"大失血"轮次**——260 次调用单次未命中就超过 1 万 token，这 260 次吃掉了全部未命中量的 **71.8%**。
所以优化目标不是"提高平均命中"，而是**掐掉那几次整段失效**。

## 三、大失血发生在哪三种场合

1. **后台苏醒 / 主动搭话轮（占比最高）**
   这类调用与"上一次调用"的时间间隔中位数是 **149 秒**，其中 43% 落在 2 分钟内、12% 间隔超过 10 分钟。
   也就是说：后台轮经常在前缀已经过期（DeepSeek 缓存 TTL 分钟级）的时候才发起，一次性把整段 system 重新读一遍。
   极端情况是凌晨轮询、整点唤醒——与前一轮隔几小时，等于全量重算。

2. **工具循环中途的追加调用**
   一次工具结果落进 messages 后，后续轮次的前缀从插入点开始全部变化；工具返回体量越大，损失越大。

3. **上下文大改之后**
   例如今天清理工作区（删掉 47 个音频文件）后，注入表 / 记忆 / 目录清单内容变动，紧接着的几轮基本全 miss。

## 四、结构性隐患（这才是能根治的地方）

### 1) system 拼装顺序：会变的块排在中间

当前顺序（`engine._system_prompt`）：

```
persona → identity(含时间戳/在场者) → nospeak → media → cq_ban
        → style → memory → task → inject
        → tools_guide → mcp_rules
```

前缀缓存是按"从头开始连续相同"生效的。**每轮都在变的内容（时钟、在场者身份、记忆、注入表）被排在中间，它们后面的一切——包括体量最大的工具说明、MCP 规范——每轮都要重算。**

### 2) 工具 schema 全量挂载，体量最大且排最后

- 内置工具 **61 个**，schema 合计 **24,921 字符 ≈ 1.4 万 token**。
- 单个体量最大的：`screen_validate` 1147、`watcher_start` 950、`schedule_add` 943、`custom_tool_validate` 941、`poll_add` 915、`history_query` 891、`click_at` 856、`read_image` 788。
- 它们挂在 system 末尾，正好是"最容易被前面变动打断"的位置；同时闲聊轮根本用不到 screen / watcher / custom_tool 这一批。

### 3) 注入表 + 记忆块按内容动态拼

- 注入表（每条上限 500 字、现有 3 条约 1500 字）和第一人称记忆每天都在改，属于"必然变化"区。
- 这两块目前也是插在前缀中间。

### 4) 后台轮与正常人轮共用同一前缀

苏醒 / 搭话轮其实不需要完整人设与全量工具，但走了同一套拼装，导致它们既贵又几乎必定 miss。

## 五、可动手的方向（按性价比排序）

1. **重排 system（改动小、收益最大）**
   不变区在前，变化区全部挪到末尾：
   `persona → identity(去掉时钟与在场者) → 固定规范 → tools_guide/mcp_rules → [记忆 → 注入 → 在场者 → 时钟 → 任务块]`
   效果：时间戳跳动、记忆更新、注入表改动都不再打断后面的工具说明。

2. **工具 schema 按场景裁剪**
   闲聊轮不挂 `screen_*`、`custom_tool_*`、`watcher_*`、`qzone_*`、代码执行类；只在真正进入对应流程时挂。
   粗估能省 5000–8000 token/轮，且让工具区更早落进稳定前缀。

3. **给后台轮（唤醒 / 搭话 / 定时）单独一套短前缀**
   短人设 + 只挂"开口说话"必需的工具，不复用主前缀。这类轮次是 10k+ 失血的主要来源。

4. **辅助调用（judge / extract / mood）把固定指令前置、变量后置**
   目前它们命中率 0.5%–27%；把固定规则写成前缀、只把"当前消息"放尾部，至少能吃到系统级公共前缀。

5. **（可选）时钟行并入末尾**
   `clock_line` 每轮都变，别让它出现在 identity 中部。

## 六、建议的执行顺序

先做 1，观察 1–2 天 chat 命中率与 >10k 次数；再做 3（后台轮前缀）；最后做 2（工具裁剪）——2 涉及工具可见性逻辑，动之前要确认不会让该用的工具临时消失。

## 七、实施状态（v2026.10.27.2）

- **建议 1 已实施（收窄版）**：`engine._system_prompt` 重排为
  `人设→身份→nospeak→媒体→CQ禁令→工具目录→MCP规范→风格→记忆→约定→注入`，
  即四个每轮易变块移到工具目录之后。在场者/时钟等**独立 system 消息**本次不动
  （移动它们会改变提示词语义顺序，需单独评估）。
  取舍：工具目录离最后一条用户消息变远、记忆/注入变近，近因效应变化待观察，
  建议盯 1–2 天 chat 命中率与 >10k 失血次数再决定是否继续。
- **建议 4 已实施（mood）**：`judge_mood` 的 system 改为常量规则前缀，
  本轮口径/幅度上限/当前心情值/七绪现状全部移到 user 消息；幅度钳制保留在代码侧。
- 建议 2（工具按场景裁剪）、3（后台轮短前缀）、5（时钟行并入末尾）**未做**。
