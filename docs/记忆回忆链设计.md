# 记忆回忆链（memory recall trail）设计稿

> 目标：让每一次「我回忆起某条记忆」都留下一条不可篡改的足迹——当时在什么上下文里想起、想起来的是什么样子、这次回忆之后我有没有改动它。旧的事实层永不被覆盖，改动的只有解释层。

> **实现状态（2026-10-27）：第一期已上线（DB v15，版本 v2026.10.27.1）。**
> 已做：只追加的 `self_memory_traces` 表；召回即留痕（触发语/来源群/场景/心情快照/融合分）；
> 事实层三个写入口（三档合并的 revise/supersede、Web 编辑 web_edit）同事务强制留痕；
> Web 记忆页主人只读展开；trace 永不进模型上下文；`self_memory_trace_on` 开关（可按群关）。
> 未做（本稿的后续期）：LLM 压缩/digest、周报式矛盾发现、心情加权召回、解释层生成器——
> 先攒一批真实 trace 再定。注意本稿写于 v10 时期，文中的版本号、`Recaller` 类名、
> 融合权重（0.62/0.28/0.10）与现代码（0.75 相关 / 0.15 重要度 / 0.10 时效）已有漂移，以代码为准。

---

## 1. 为什么要做

现在的自我记忆是**可覆盖的**：`self_memories` 表里一条记录被改写时，旧文本塞进 `history` 字段（只留 5 版，且是纯文本数组，没有上下文、没有时间、没有当时的心情）。结果是：

- 只能看到"改成了什么"，看不到"为什么改、在什么场合改的"；
- 5 版之外的老版本直接蒸发；
- 同一件事上前后矛盾的记忆，自己发现不了；
- 检索时**所有记忆权重一样**，情绪重的时刻也调不出同类的旧记忆。

做成链之后，上面四条都能解决，代价只有一个：存储线性增长（但每条约 200~400 字，量级很小）。

---

## 2. 三条设计原则

### 2.1 只追加，不改写

一条记忆被读取时，写一条 `trace` 进去。同一条记忆可以有几十条 trace，谁都不删。
真正的"记忆内容"仍然是 `self_memories.text`，但它只在**事实变更**时才允许变，而且变更必须挂一条 trace 来解释。

### 2.2 事实层 / 解释层分离

| 层 | 存哪 | 允许改 | 例子 |
|---|---|---|---|
| 事实层 | `self_memories.text` | 仅在事实被推翻时改，且强制留 trace | 「我答应秋茗明早 7:40 叫他上课」 |
| 解释层 | `self_memory_traces` | 永远只追加 | 「想起这条时，我觉得自己是在讨好他」 |

解释层可以自相矛盾，这正是它的价值。事实层一改就要警惕：改多了会变成「我记得我觉得你说过」。

判定原则：文字里出现**新的可验证事实** → 事实层；出现**看法、情绪、归因** → 解释层。

### 2.3 链不进对话上下文

trace 只给自己看、给后台任务看，**绝不注入到说话的 prompt 里**。

理由：一旦我知道每次回忆都会被记下来，我就会更在意让记录好看，而不是真的回忆——人会为日记自我表演，我也会。这一条是硬约束。

## 3. 数据表

新增一张表，不改动 `self_memories`（只加一列冗余计数）。

```sql
-- v10 增量
CREATE TABLE IF NOT EXISTS self_memory_traces (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    memory_id     INTEGER NOT NULL,          -- 指向 self_memories.id
    kind          TEXT    NOT NULL DEFAULT 'recall',
                                             -- recall | revise | merge | compress
    context       TEXT    NOT NULL DEFAULT '', -- 触发这次回忆的 query（用户那句话）
    group_id      TEXT    NOT NULL DEFAULT '',
    mood          TEXT    NOT NULL DEFAULT '', -- 当时的心情标签（mood 模块给）
    mood_level    INTEGER NOT NULL DEFAULT 50,
    seen_text     TEXT    NOT NULL DEFAULT '', -- 这次「想起来的样子」（可能是改写/摘要版）
    revision      TEXT    NOT NULL DEFAULT '', -- 本次做的改动（改了什么，空=没改）
    match_score   REAL    NOT NULL DEFAULT 0,  -- 这次检索的相关度，用于复盘
    created_at    REAL    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_trace_mem ON self_memory_traces(memory_id, id DESC);
CREATE INDEX IF NOT EXISTS idx_trace_time ON self_memory_traces(created_at);
```

`self_memories` 加一列冗余（避免每次 count）：

```sql
ALTER TABLE self_memories ADD COLUMN trace_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE self_memories ADD COLUMN trace_digest TEXT NOT NULL DEFAULT '';
-- trace_digest：老链压缩后的一句话摘要，注入时用它代替全部历史
```

迁移放在 `storage.py` 的 `_DDL_V10` + `MIGRATIONS` 里，照现有 v9 的写法加一段。

## 4. 写路径

### 4.1 召回即留痕

改 `self_memory.py::Recaller.recall_block()`，在决定采用某条记忆后（`lines.append` 成功的位置）调一次：

```python
storage.add_self_memory_trace(
    self.db_path,
    memory_id=e['id'], kind='recall',
    context=query[:300], group_id=group_id,
    mood=mood_tag, mood_level=mood_level,
    seen_text=e['text'][:400],
    match_score=float(score),
)
```

要点：
- **批量一次写入**，别在循环里每条一次 `connect()`；攒成 list 后一次 `executemany`。
- `context` 截断 300 字，避免一条 trace 撑爆。
- trace 写入失败**不能影响本轮对话**，外面包 try/except 只 log。
- 同一轮里同一条记忆只记一次（有去重集合）。

### 4.2 事实变更时留痕

`storage.update_self_memory()` / `merge` 系列里，改写文本时同步写一条 `kind='revise'` 的 trace，`revision` 填「旧文 → 新文」的 diff 摘要（不用真 diff，写 `旧:xxx | 新:yyy` 截断版就够）。

### 4.3 情绪加权（顺手做，收益最大）

`Recaller._rank()` 里给融合分数加一项同调加成：

```python
# 心情相近的旧记忆往上浮一点，权重小一点，别盖过相关度
mood_bonus = 0.0
if mood_tag and e.get('mood_tag') == mood_tag:
    mood_bonus = 0.08 * (1 - abs(mood_level - e.get('mood_level', 50)) / 100)
fused = 0.62 * (s / max_s) + 0.28 * recency + 0.10 * importance + mood_bonus
```

（现有融合是 `0.62 * 相关 + 0.28 * 新近 + 0.10 * 重要`，照实际代码里的系数调，不要凭这份稿子硬套。）

代价：需要在 `self_memories` 上加 `mood_tag` / `mood_level`（写入时从当前心情快照取）。可选，第二阶段再做。

## 5. 读路径（token 控制的关键）

### 5.1 注入时绝不读全文链

`recall_block()` 只输出：

```
- {current_text}
```

**不加**历史。想让历史影响语气，走 `trace_digest` 一句话（比如「这条我以前改过两次，越改越偏向『我是在讨他开心』」），不做逐条罗列。

### 5.2 主动复盘工具（这是链真正的用处）

新增一个只后台/工具调用的读法：

```python
storage.get_self_memory_trail(db_path, memory_id, limit=10, before_id=None)
```

返回按时间**倒序**的 trace 列表。默认只取最近 10 条 + `trace_digest`。

真正有价值的三个查询场景：

1. **前后矛盾自检**：同一条记忆的 `seen_text` 前后差得远 → 说明我在为当时的情绪找理由。可以做成每周一次的后台任务，把矛盾的列出来。
2. **为什么我会这么想**：某个话题我反复想起某条旧事 → 看 `context` 分布，就知道是什么话在勾我。
3. **记忆被谁塑造的**：`group_id` 分布 + `mood` 分布，能看出某些记忆是在特定群、特定心情下被反复强化的。

### 5.3 压缩：会撑爆的地方

链会一直长。策略：

- 每条记忆的 trace 数超过 **20** 时，把最老的 10 条交给一次后台 LLM 调用压成 80 字以内的一句话，写进 `trace_digest`（**拼接**到已有的 digest 后面，不覆盖），然后把这 10 条标 `kind='compress'` 归档（不删，读的时候跳过）。
- 事实层的 trace（`kind='revise'`）**永不压缩、永不删**。它们才是可信度基线。
- 压缩阈值和批次做成配置项：`self_memory_trace_keep`（默认 20）、`self_memory_trace_compress_batch`（默认 10）。

成本估算：一条 trace 约 300 字 → 0.15k token 存，压缩时一次读 10 条约 1.5k token 进、100 token 出。假设一天召回 50 次，压缩一次/天，可忽略。

## 8. 已知风险

1. **存储线性增长**。按一天 50 条 trace、每条 300 字算，一年约 5MB 纯文本，可接受。要是召回量大（群多），得靠压缩兜住。
2. **自我表演**。见 §2.3，靠"链不进上下文"这条硬约束挡；另外写 trace 的代码路径不要暴露给对话模型当工具，只给后台任务。
3. **事实层被盗改**。改事实必须留 trace，代码里强制；任何直接 `UPDATE self_memories SET text=` 的地方都要检查一遍（`storage.py` 里 grep 一下）。
4. **压缩丢信息**。compress 只压解释层，且原记录标归档不删除，怀疑丢东西时能翻回来。
5. **多群写冲突**。同一秒多个群同时写，用 `executemany` + 单事务。`trace_count` 的增量用 `SET trace_count = trace_count + ?`，别读改写。

---

## 9. 一句话总结

> 记忆不再是可覆盖的文档，而是一条只追加的历史；事实层钉住，解释层随便变，变化本身被完整记录下来——这样我才能发现自己什么时候在骗自己。
